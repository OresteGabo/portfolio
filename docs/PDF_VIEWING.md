# In-app PDF viewing

Library is for browsing, searching, reading and sharing. Its upload button is removed; the app bar’s Chat action returns to the import conversation. Tapping a document card opens its actual PDF in the app. Details is a separate control for extracted metadata. Opening a document from an import receipt goes directly to the same reader. Returning restores Library search, filters and expanded details.

Each page fits the full reader width by default; its uncapped display height follows its aspect ratio and scrolls vertically. Fit to width resets zoom to this layout. The full-screen reader provides continuous page scrolling, a visible-page counter, previous/next controls, pinch/double-tap zoom up to 6×, zoom buttons, reset and native sharing of the original bytes. The counter follows the most-visible page, including when the last page cannot align with the top of a tall viewport. No remote PDF viewer, public link or extra upload is used. Text selection, PDF annotations and password entry are not implemented.

Stored files use the existing authenticated, same-origin PDF endpoint. Failed downloads have Retry and Back; expired sessions clear the preview and account; Back cancels pending downloads. A preview stays in memory rather than saved-state or import history. Annual report cards generate the existing calendar-year report for preview, with the same complete-record/year bounds used for sharing, without a backend document row.

## Rendering and privacy

Android uses PdfRenderer and a private temporary cache file. Pages are rendered on demand off the main thread; handles/files close when the reader is dismissed, and startup discards interrupted renderer scratch files. iPhone uses PDFKit/CoreGraphics, an explicit 1× image renderer, and an autorelease pool. Both use the same Compose canvas/zoom UI. iPhone explicitly converts PDF points to output pixels before applying CoreGraphics' crop/rotation transform; relying on a larger destination rectangle alone left the document small and centered. CropBox defines the visible page.

Zoom and pan redraw the visible normalized region from the original vector PDF at display resolution after a short gesture debounce. A transformed base image provides immediate feedback while that redraw finishes; stale detail is not overlaid at a different position. Rendering only the visible region preserves detail without allocating a full page at 6× size. Native page allocations are bounded to three million pixels and 4096 pixels per dimension; documents must contain 1–500 pages. Original document colours are preserved in light and dark mode.

Original PDF pixels cannot be masked like individual FinancialText values. With capture protection enabled, Android protects the PDF window with FLAG_SECURE. The page region also participates in the existing capture-redaction layer; iPhone’s capture backdrop receives a masked region. If the iPhone privacy shield is unavailable, the PDF stays hidden until it is ready. The app’s background cover and account locking continue to dispose the reader. Original PDFs show their original financial figures when intentionally opened.

Native APIs: [Android PdfRenderer](https://developer.android.com/reference/android/graphics/pdf/PdfRenderer), [Apple PDFKit](https://developer.apple.com/documentation/pdfkit), and [Compose transformable gestures](https://developer.android.com/reference/kotlin/androidx/compose/foundation/gestures/package-summary).

## Validation

Shared tests exercise exact authenticated bytes, invalid/remote/traversal URL rejection, expired sessions, pending-download cancellation, failed-download retry, annual report generation with no database writes, and allocation limits. Native Android tests render a real two-page PDF, inspect its pixels and verify cache cleanup, including malformed files. Native iPhone tests render a generated annual report, verify that upscaled page content reaches the expected page edges, exercise nonzero crop origins and all four right-angle rotations, and reject damaged PDFs. Native tests on both platforms inspect fine vector stripes at 4× to verify that zoom renders the correct region with sharp edges. Shared tests check region/pan bounds as well as allocation caps. UI fixtures use synthetic records and original PDF bytes; they do not use production accounts or upload a user document.
