# Document import conversation

Documents opens to Library by default. Its prominent floating **+ Add document** button above the bottom navigation opens the native PDF picker immediately; selecting a file moves into Import chat for reading, review, upload progress and the final receipt. Cancelling selection keeps the current screen. Returning through the Documents navigation item always opens Library. The Chat shortcut remains available for import history and unfinished reviews. Documents has two sections. **Import** is a native conversation for attaching PDFs and reviewing their detected type, progress, errors and final result. **Library** retains searchable documents, separate metadata details, native PDF sharing and generated annual reports. Its + action starts a new upload, and its Chat shortcut opens Import history. Tapping a file opens its original PDF in the [in-app reader](PDF_VIEWING.md). Import hides the bottom navigation and uses one compact app bar with the Struct Capital logo/name and account, Back to Library, and a direct Library/Import switch; leaving the conversation preserves an unfinished review. Its neutral introduction sits outside the message history and can be dismissed with ×, with dismissal remembered on the device. PDF attachment bubbles are right-aligned with a left gutter; Struct replies are left-aligned with a right gutter, a brand avatar and an opposite bubble corner. Both sides have capped widths on larger screens. The chat has a stationary native wallpaper with faint geometric seals, document outlines and graph motifs over a soft theme-aware wash; linework is lighter through the centre and stays behind opaque message cards. Cached vector paths require no downloaded image or animation. When the account has no local import receipts, a centred first-use guide explains the supported PDF types and points to the existing attachment control. It is unframed and scrolls on smaller screens; it disappears as soon as a real import starts. Existing Library documents are not treated as chat activity. There is no free-text assistant or remote chat model.

All existing PDF entry points, including Portfolio Add purchase, pending-purchase confirmations, missing-document actions, Android Share/Open with and iPhone Open In, route into the same conversation as soon as a file is selected. Selection events are separate from receipt IDs, so retries also route correctly. Source-screen overlays close while the receipt retains the original target purchase/statement context. The account email identifies the destination. Local parsing identifies personal bond confirmations, share contracts, public bond issuance reports and BK Capital statements. Review stays available when switching tabs; financial writes still require the explicit review action.

A single save action uploads the original PDF and saves/confirms the corresponding investment. A public issuance saved independently does not assume a personal allocation. A statement stores its original PDF and checks the existing statement-items endpoint; missing contracts remain reminders rather than adding unconfirmed investments. Completed messages use a document receipt with a type label, PDF cover, saved instrument/date/issuer and the matching investment logo when identifiable. Share logos identify the company rather than its broker; unsupported identities keep the PDF artwork. Receipt details are read from actual loaded records and are not added to local journal storage. Receipts link to the real document and, for bonds, the purchase details. Deleted or unavailable documents show an explicit Library message.

## Retry and persistence

The device stores account-scoped import receipts: filename, timestamps, status, PDF SHA-256, safe error text and real record identifiers. It retains the latest 1,000 imports and up to eight earlier attempt outcomes per import. It does not persist raw PDF bytes, extracted fields, investment amounts, passwords or session tokens in the journal. This history is local to the installation; it is not a server-synced conversation.

An active PDF stays in memory for retrying a failed parse or save. After a restart, interrupted work asks for the same PDF again and checks its fingerprint before reusing its uploaded document. Uploaded document IDs and upload tokens are reused on retries. Lost purchase responses are resolved against existing records before creating a new record. An uncertain or conflicting match stops for review. Successful purchase confirmations can also reconcile interrupted receipts from the actual server records. Signing out detaches the account history; deleting the account removes its local journal.

Shared tests cover journal restoration/account isolation, hashing, safe metadata persistence, same-file retry checks, upload reuse after failed saves, lost purchase responses and statement reconciliation. Android UI coverage uses synthetic PDFs and a localhost fixture for parse failure, retry, inline pending-purchase review, tab switching, save failure/retry, real Library/purchase navigation and history after relaunch in dark mode. The journey passes on a normal viewport and at 360 × 640 with 115% font scale; the compact run also checks shared-file routing and French display. All 167 Android host and 176 iOS simulator tests pass, and the full Android and iPhone simulator apps build. No production account or upload is involved. Existing native PDF handoff limitations are described in [PDF sharing](PDF_SHARING.md).


## Existing PDFs

After local parsing, import checks the current account’s fresh Library list. A matching account-scoped receipt fingerprint can identify a document that still exists. For older/cloud documents, filename, type, instrument and date metadata narrow the candidates; authenticated PDF downloads and SHA-256 establish whether their contents are identical. Metadata alone never suppresses a different PDF. Verified fingerprints are cached only in account-scoped memory. Deleted files and another account’s receipts do not block a new import.

A duplicate produces an **Already in Library** receipt linking to the real document. Fresh purchase/holding records establish whether its purchase details are also already saved; already-confirmed targeted imports stop at this receipt instead of opening another save review. A genuinely pending confirmation still offers Confirm using saved PDF, without another file upload. Statement/issuance receipts distinguish completed records checks and saved public terms from personal purchase confirmation. The original server creation time is shown when provided; otherwise the earliest successful local receipt is labelled First saved on this device. A document issue/trade date and a repeat-import attempt are never presented as the original upload time. If no trustworthy time is available, it is omitted. It does not upload another PDF, create an investment or claim that a pending purchase was confirmed. A specific pending-purchase import and an interrupted import with a saved source PDF can reuse that file for the remaining explicit confirmation. The save action checks again before its first upload in case another import completed while review was open. Network/check failures stop the write. These are client preflight checks against the existing API; a globally atomic guarantee for simultaneous uploads would require a backend storage constraint.

## Library summaries and detail navigation

Updated 1 November 2026. **Details** expands a compact, theme-aware summary: instrument, issuer and at most two lines of description, followed by a clear destination action. It no longer expands every parsed fact, fee and statement section inside the Library list. Tapping the file itself still opens its original PDF; sharing remains independent of expansion.

A single explicitly linked bond opens the existing Bond details page. A single linked share position opens the existing Share details page, grouped by ticker and currency rather than individual purchase lot. Links use persisted confirmation/issuance/contract/statement document identifiers on the current account's loaded investments; matching names, dates or company labels never invent a relationship. Several related investments or another document type open **Document details**, with related-investment choices where available. If investment history is incomplete, that page offers the existing history load/retry.

The separate document page retains issuer/date/filename, every saved parsed fact/charge/section, original PDF preview and sharing. Annual reports retain their explicit generation warning and progress feedback. A secondary Document details action remains available on the compact bond/share summary. Back returns to the prior document page or Library state, and child detail pages hide the main navigation. Existing authentication, financial masking, document ownership and public-issuance policy are unchanged; no backend/API or financial calculation changes are required.

## First-page content previews

Saved Library PDFs have a narrow first-page window above the document identity. It shows a genuine native-rendered excerpt (top 40% of page one), with a First page label, rather than a fabricated cover or extracted financial summary. Tapping the image opens the existing full-resolution PDF reader. Issuer/company identity, summary disclosure, sharing and detail routes remain below it. Generated annual reports keep their branded cover and explicit generation workflow.

The existing authenticated PDF endpoint and Android PdfRenderer/iOS PDFKit implementations are reused. Previews load independently of the model's global busy/error states, only as lazy-list items are composed near the viewport. Downloads/decoding are serialized and optional loads have an eight-second coroutine timeout. Failed previews retain an Open PDF fallback rather than an error page; retrying the full reader remains possible. The session-memory LRU retains at most eight results and four MiB of image pixels, including failed outcomes to avoid automatic retry loops. Account/session clearing and model disposal clear the cache. No rendered preview is written to disk; the Android renderer uses its existing private temporary PDF and closes/deletes it after rendering.

Hide numbers replaces the entire image with a privacy placeholder; numbers cannot be reliably masked inside arbitrary PDF pixels. No preview download starts while hidden. Capture-protected previews use the same redaction wrapper and native-shield readiness gate as the PDF reader. Preview labels do not expose extracted text to accessibility.

This client-only implementation downloads the original saved PDF on the first visible preview request after a cache miss (subject to the existing 24 MiB response limit), then retains only the small rendered excerpt. It does not fetch every Library file at startup. The memory cache intentionally does not survive a lock or process restart. If larger libraries/files make transfer cost significant, investigate authenticated server thumbnails under the existing ownership policy; do not add public thumbnail URLs or an external rendering service.
