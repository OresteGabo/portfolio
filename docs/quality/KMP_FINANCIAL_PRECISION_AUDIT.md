## Verified correction and intentional behavior change

**Medium — `InvestmentLedger.validateLedgerEntry` sale admission used binary `fees + tax <= gross`.** Before production edits, the characterization suite reproduced rejection of one share sold at 0.30 with 0.10 fees and 0.20 tax. Binary addition produces 0.30000000000000004; decimal charges equal proceeds and satisfy the existing “cannot exceed proceeds” rule.

The new internal `SaleCharges.kt::saleChargesWithinProceeds` compares non-negative decimal input values without rounding or epsilon. It aligns the finite Double texts as unsigned decimal integer digits, adds the two charges with integer carry and compares against proceeds. Scientific notation, signed zero and extreme finite exponents are covered. Work is bounded by finite Double text (roughly 650 columns), not arbitrary user-supplied digit strings. This narrowly scoped admission primitive avoids a new dependency or a general-purpose decimal framework. It also avoids binary sum overflow and Foundation decimal exponent/precision limitations in this comparison. It cannot recover digits already lost on Double input.

The only production call-site change replaces the sale charge comparison. Gross cap, quantity/price/fee validation, formulas, error text, cost allocation, recorded amounts and rounding stay unchanged. The corrected case now returns zero net proceeds and -0.30 realized gain for a 0.30 acquisition cost. Charges 0.10 + 0.200000001 still fail: rounding the charges to cents or adding a tolerance would incorrectly permit an excess. Conversely, the new comparison rejects excess charges previously hidden by binary rounding: 0.30 + 1e-300 is greater than 0.30, even though binary addition can erase the tiny positive charge. This stricter admission is intentional and tested; it does not round away supplied charges. No old saved event is recalculated or rewritten.

The initial characterization test expected the reproduced failure. After correction it asserts the intended successful result; an additional test covers rejection above the limit. The independent JVM oracle checks 2,744 boundary combinations plus 6,000 seeded near-sum comparisons against BigDecimal. Common tests execute on every tested KMP runtime, including tiny positive charges and very large finite inputs. Existing decimal money implementations are byte-for-byte unchanged.

## Representation decisions

Retain the existing decimal implementations for monetary products/division/rounding and existing Double serialization compatibility. Rates/ratios/progress are not money and are not rounded to currency scale. Whole quantities and price/tax precision differ from recorded monetary outputs. Scaled Long is a good option only when scale/range are known and checked: blindly multiplying current 1e15 bounds by 100 or migrating all rates/prices to cents would be incorrect. Foundation decimals are the existing native capability, not unlimited precision. A wider exact domain/wire representation remains a deliberate migration, not part of this validation fix.

No financial formula, rounding mode/stage, currency policy, stored schema, backend contract, PDF parser tolerance or UI design is changed. The documented sale admission correction is the sole intentional numeric behavior change. Remaining ambiguities above have no unverified implementation change in this commit.
