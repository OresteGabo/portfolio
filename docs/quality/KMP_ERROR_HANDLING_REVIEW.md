## Implemented contracts

### Transport and decoding

`network/ApiFailures.kt` introduces two small exception types without a base hierarchy or new dependency:

- `ApiResponseException`: a successful HTTP body cannot satisfy the existing JSON object contract. Wraps the decoder's IllegalArgumentException only inside record decoding; original cause remains available.
- `ApiTimeoutException`: wraps Ktor 3.6.0 HttpRequestTimeoutException, ConnectTimeoutException or SocketTimeoutException. The pinned library's common/non-JVM contracts were inspected locally. Original platform/library cause remains available.

Both messages instruct the user to **refresh before trying again**, since a timeout or unreadable successful response does not prove a submitted write failed. `ApiException` and HTTP status/authentication handling remain unchanged. Unexpected exceptions and fatal errors are not turned into timeout, empty records or success. There is no automatic retry, changed deadline, API payload change, status remapping, session invalidation or new network request.

`UserFacingErrors` approves only the new fixed messages; French translations are supplied. It does not display causes or arbitrary decoder/transport text. Startup now distinguishes unreadable server data from an inability to connect. Existing server validation/status/PDF messages and already-saved-but-refresh-failed warnings remain intact.

### Cancellation and diagnostic outcomes

`PortfolioApi.bytes` rethrows caller CancellationException and labels its timing span cancelled. Known Ktor transport timeouts are labeled timeout. Other failures during response reading are failed; non-success HTTP status remains a numeric status outcome. `UnlockPerformance.measure/measureSync` also distinguish cancellation from failure while rethrowing the caught object.

Existing diagnostics remain opt-in, route-whitelisted and free of error/body text. A random request ID is not a transaction ID. A malformed successful JSON body can legitimately produce an HTTP 200 timing plus failed JSON-decode timing: transport succeeded, representation did not. A body-read/size failure is not labeled successful transport completion. The diagnostic sink still cannot throw into business operations.

Coroutines/Ktor can copy exceptions during asynchronous stack-trace recovery. Integration tests assert preserved type/message and retained diagnostic cause, rather than promising reference identity of the MockEngine's original thrown object across the library boundary. Direct wrapper and direct measurement propagation tests retain exact identity assertions. The first focused test run failed two overly strong async identity assertions; tests were corrected to the actual library contract, with no production workaround. Final focused and full verification results are below.

### Optional journal persistence

`ImportJournal.persistenceFailed` remains the existing read-only boolean observed by callers; it now derives from `persistenceFailure: Exception?`, which has a private setter. Ordinary read/write failures preserve their original cause in memory. Causes are never serialized into receipts, shown directly or sent to logs. Successful later persistence clears the diagnostic. Detach clears account-bound diagnostics.

Switching accounts first detaches the old account and clears its receipts/diagnostics. New read ownership/state is published only after a read that was not cancelled, so a cancelled replacement read cannot expose the previous account's history. A cancelled initial attach can be attempted again for the same account rather than silently binding it to an empty result. Cancelled writes propagate; in-memory receipts remain available for the next explicit update/write. Fatal errors are no longer converted into optional storage failure. No financial import is claimed persisted merely because history persistence succeeds, and a history write failure does not undo a confirmed investment save.

The existing recovery policy remains: a subsequent receipt mutation attempts persistence again; reattachment/restart reads history again. This is not a timer/background retry service or a new UI retry control. Same-account attach alone still does not force a reload. Corrupt history decoding still follows its existing bounded empty/skip recovery policy; changing that requires a separate data-recovery decision.

## Remaining focused follow-ups

1. Optional notification/provider errors lack sufficient explicit availability/cause state. Preserve primary-screen recovery and permission/session semantics before replacing their best-effort catches.
2. Guest/import/migration UI errors are often safe fixed messages but discard detailed causes. Structured internal diagnostic codes may help; do not forward PDF/JS/SQL/platform messages into UI or remote logging to gain visibility.
3. Domain validation and parser warnings still use message strings at some boundaries. Introduce typed internal validation where it removes real ambiguity, preserving serialized/API contracts and current warning admission.
4. Non-timeout platform connection/TLS errors continue through their existing propagation/fallback path. This patch classifies the three common Ktor timeout types, not every Darwin NSError/Android network provider error. Mock tests do not prove every physical network error mapping.
5. ViewModel boundaries intentionally catch ordinary exceptions to show recoverable UI state, including unexpected programming failures. A privacy-reviewed diagnostic reporting policy would be needed to observe those in production; no crash collector, remote logging or global error bus is introduced here.
