# KMP client security-focused review

Reviewed 15 November 2026 against `7b37d5b`. Scope: the mobile client, platform implementations and shipped dependencies. Backend authentication/authorization/endpoints, website and infrastructure are untouched. No production credentials, real customer files, live account requests or invasive device tests were used. This is a source/regression/dependency review, not a penetration test or proof of absence of vulnerabilities. The 39 pre-existing unfinished entries remain outside this commit.

## Prioritized findings and focused fixes

| Finding | Severity / exploitability | Evidence and impact | Resolution |
|---|---|---|---|
| CSEC-01: iOS export staging lacked an explicit protection/retention policy | Medium, local at-rest hardening; not a remote auth bypass | `app/shared/src/iosMain/.../PlatformPorts.ios.kt::savePdf/sharePdf` created ordinary UUID temp directories with unchecked directory creation and atomic writes without a file-protection option. Normal finally cleanup existed, but no owned stale-file namespace or explicit Complete Data Protection covered report/PDF/backup staging. The app entitlements do not establish a stronger default class. All protection/write setup returns must succeed. Cleanup runs after success, failure and cancellation, including cancellation while the URL returns from the write dispatcher. Only expired UUID directories in the owned root are eligible for opportunistic cleanup on a later export. |

| CSEC-02: cancelled queued PDFs were dropped without clearing their buffer | Low, residual-memory exposure | `IncomingPdf.kt::PdfImportInbox.dismiss` dropped the reference without clearing the pending buffer. No remotely exploitable authentication bypass was established in the inspected paths. That is an audit observation with the limits below, not a security guarantee. These focused fixes preserve account/guest routing, supported document formats, legitimate filenames/extensions, chooser behavior, authentication and biometric flows. No cryptographic algorithm, key format or backend contract was introduced or changed.

## Protection and cleanup contract

The iOS helper stages only user-requested exports; it is not a new persistent portfolio store. Apple documents Complete File Protection as limiting access to the unlocked device; atomic writes use an auxiliary file before replacement. Both the containing directories and Foundation write options now request the protection, without simulator-specific production branches. See [Apple Foundation file-protection options](https://developer.apple.com/documentation/foundation/nsdata/writingoptions/fileprotectionmask).

Only sanitized single-component names are used (ASCII filename characters, bounded to 240 characters, with `.`/`..` falling back to a safe name). Existing share names with an appended `.pdf` and encrypted-backup extensions remain intact. Caller bytes remain unchanged. Cleanup uses NonCancellable solely to release the operation's own staging directory; it does not make import/network work uncancellable. Removal is best-effort if the OS refuses deletion; protected leftovers can be retried by the next owned-root sweep or OS cache management. This is not guaranteed timed erasure.

Crash leftovers in the **new** staging root older than 24 hours are pruned on a subsequent export. The sweep never traverses arbitrary temp folders or original/provider-selected documents. Old UUID temp directories outside this root are deliberately not guessed/deleted. Copies explicitly saved or shared by the user belong to the selected destination/recipient and are not removed by app cleanup.

Mailbox clearing is best-effort hygiene for a specific owned array, not a secure-memory allocator or a promise to erase every PDF/NSData/String/parser/OS copy or crash-memory page. The importer owns data after take; its existing completion/cancellation lifecycle remains responsible. Ingress callers transfer their buffer on an accepted offer; rejected offers retain caller ownership. No extra persistent PDF copy is introduced. Unavoidable temporary managed/native copies remain a limitation.

## Inspected client controls and remaining findings

| Area | Actual controls / remaining limits |
|---|---|
| Authentication and tokens | `PortfolioApi` owns in-memory cookies. Persisted session/password snapshots go through SecureSignIn when the user enables that feature, not ordinary connection preferences. Cookie snapshots are origin-bound, bounded and expiry-aware; HTTP status/session invalidation semantics remain server-authoritative. This review does not redesign endpoints or replace the existing saved-password fallback with a token scheme. Immutable strings can remain in managed memory until collection. |
| Android biometric vault | `SecureSignIn.android.kt` uses AndroidKeyStore authentication-bound wrapping keys and platform AES-GCM. Android 11+ authorization is per operation; older versions deliberately use the existing short device-credential authorization window. Data keys clear on lock; prompts/continuations cancel and Activity ownership is weak/detached. No test credential/Keystore bypass or new encryption scheme is added. Real enrollment/lock/tamper behavior still needs physical-device checks. |
| iOS biometric vault | `SecureSignIn.ios.kt` uses passcode-bound ThisDeviceOnly Keychain items with user-presence ACL and LAContext invalidation. Defaults contain presence metadata, not the secret itself. Platform password-manager save remains user-mediated. Simulator tests do not prove Secure Enclave or device passcode enforcement. |
| Session lifecycle | `PortfolioModel` and feature owners use generation/owner checks, cancel active work, clear account data and lock the vault. `SessionState` distinguishes guest, signed-out and verified account identity. Existing session/lock/switch tests remain authoritative; the unfinished unrelated ViewModel changes are not committed here. No navigation intent grants a verified identity. |
| Personal guest mode | Intentional **durable local** portfolio/PDF storage is part of the implemented feature, not accidental ephemeral persistence. Android uses separate non-exportable Keystore keys, AES-GCM ciphertext and no-backup storage; iOS uses Complete Data Protection, atomic writes and backup exclusion. Missing keys, corruption and protected reads do not silently overwrite originals. Device protection is not a new independent biometric app lock. Deleting this data on guest exit would break the product and is not done. |
| Sample/temporary guest paths | Sample mode and private import adapters avoid authenticated upload and native copy-on-open where private access is supported. Guest import bytes/preview are cleared by their current owners and only confirmed personal saves persist. Switching to account mode discards queued guest ingestion. The new mailbox owns and clears its cancelled buffer on both platforms. Existing local-only/transfer-consent tests run; no guest file is sent to OSV or telemetry. |
| iOS share-extension queue (retained policy) | `app/iosApp/SharedImport/SharedPdfInbox.swift` stages a bounded PDF plus metadata in an entitled App Group with CompleteUntilFirstUserAuthentication, coordinates access, rejects an existing waiting item and expires it after 24 hours on later access. The app drains it only into the normal review flow. Its queue directory is now explicitly excluded from backup. Its unchanged protection class still permits weaker locked-device access than the Personal guest store, and it shares a group with signed widget code. Keep it as a medium-priority protection/least-privilege follow-up: background-delivery availability and group separation need their own workflow checks before changing that contract. The private export helper does not change that queue's protection class or delivery contract. Previously created external backup copies are not retroactively deleted by setting an exclusion flag. |
| Android temporary PDFs | FileProvider is unexported, exposes only `cache/pdf-share/`, sanitizes names and grants per-file temporary read access; no write, prefix or persistable grant is requested. This matches Android's [FileProvider guidance](https://developer.android.com/reference/androidx/core/content/FileProvider). Cleanup is opportunistic on later sharing, not an exact TTL. Immediate deletion at Android chooser return can break a recipient still reading, so iOS completion cleanup is not mechanically imposed there. Renderer temp files close/delete separately; sandbox and backup exclusions still matter. |
| File/intent/deep-link access | Android incoming streams require content URIs and bounded reads, close streams and use fixed errors. iOS local URL reads release security scopes and delete only app Inbox copies under the existing constrained rule. App/shortcut deep links use action whitelists/date parsing and normal authentication/review; they do not directly execute financial saves. External browser actions accept HTTP(S), not javascript/file schemes. No recipient/export destination is treated as an authenticated backend origin. |
| Network policy | Production API origin checks require HTTPS; debug development HTTP remains deliberately bounded by host/build flags. iOS ATS has local-network permission rather than a global arbitrary-load exception; shared release origin validation still applies. Ktor uses platform/default trust, disables redirects for private requests and isolates public quotes from credentials (including Darwin system-cookie/cache controls and Android global CookieHandler guard). No trust-all TLS/hostname bypass was found in the inspected client configuration. Absence of certificate pinning alone is not labeled a vulnerability. |
| Ordinary preferences (retained limit) | Account import filenames/IDs and monthly target preferences remain ordinary settings metadata; iOS preference backup policy is not migrated here. They are not credentials, but can be private financial metadata. Minimize or protect them in a deliberate compatibility change; do not claim every iOS preference is excluded from backup. |
| Backup/export | Android cloud/device extraction excludes app data; iOS guest files are excluded. Explicit encrypted backup export/import uses existing platform cryptographic facilities and versioned envelopes; no custom cryptography is added. A user-chosen external document destination is outside these app-only exclusions. New iOS staging also protects encrypted-backup copies consistently. |
| Financial logs/crash data | Existing timing diagnostics expose fixed stage/status/route labels and random correlation IDs, not request bodies or URL queries; safe error/progress allowlists remain. Native JS errors are reduced to fixed/typed messages. Android capture fallback warnings are separate platform warnings, not identified financial-content logs, and were not removed blindly. Retained diagnostic causes and in-memory portfolio/PDF data are **not** safe raw crash-report payloads; no remote crash collector or full crash-dump privacy guarantee is introduced. |
| Release/capture boundary | Native privacy cover, masking and Android FLAG_SECURE defaults remain unchanged. Experimental capture behavior remains an opt-in development path with existing release exclusions/tests. Actual OEM capture/recents/recording and physical-device protected-data behavior were not re-certified by emulator/simulator compilation. |

## Regression tests and verification limits

Two additional common mailbox tests cover clearing the accepted buffer and its retained aliases, rejected-delivery input preservation, duplicate suppression and take ownership. Existing fixtures now transfer fresh buffers instead of reusing their template array. The original guest-mode transition wipe assertion remains unchanged. Four native export tests use synthetic bytes and check path/name containment, unchanged input, legitimate PDF/backup extensions, backup-exclusion metadata, available protection-class metadata, success/error/cancellation cleanup and owned-only stale pruning. No original user file is touched.

The simulator may expose no file-protection-class attribute; the test requires a simulator environment in that case, and asserts Complete protection whenever metadata is exposed. Production always requests/checks the same platform operations with no simulator-specific weakening. These tests **cannot** establish actual encryption/locked-device denial, physical biometrics, Keychain/Keystore tamper resistance or resistance to a rooted/jailbroken process. Those remain physical-device verification tasks.

An initial isolated full suite caught a proposed buffer copy violating the existing guest-transition input-wipe contract; the copy was removed and the original regression remains unchanged. The first native test compilation also found test-only Foundation type/date-constructor interop errors; those were corrected without relaxing production protection or cleanup. Final source checks and results are recorded below. The Swift queue harness also asserts actual backup-exclusion metadata while keeping its existing header/size, path/name, duplicate/pending, delivery-match and expiry checks. Existing guest/account isolation, secure-session, crypto/backup, file-envelope, PDF import and safe-error tests are included in full verification.
